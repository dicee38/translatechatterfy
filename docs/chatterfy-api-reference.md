# Справочник по API Chatterfy — всё подтверждённое реальным трафиком

Сводный документ по обоим проектам (Chat Summarizer + AI Translator).
Ничего здесь не придумано — каждый пункт либо подтверждён HAR/ручным
вызовом, либо явно помечен как непроверенное предположение. Цель —
не передоказывать одно и то же в новом расширении.

Базовые домены:
- Фронтенд: `https://v2.chatterfy.ai`
- API: `https://migration-api.chatterfy.ai`

## 1. Авторизация

**Подтверждено:** заголовок `authorization: <JWT>`, **без** префикса
`Bearer`. Токен ищется в `localStorage`/`sessionStorage` страницы
(обе точки, точное имя ключа хранения не зафиксировано отдельно —
искать по содержимому, похожему на JWT). Ручной override на случай,
если автопоиск не сработает на другом окружении: `ChatApi.setAuthToken('<jwt>')`.

**Отвергнутая гипотеза:** `credentials: "include"` (куки браузера).
Не работает — сервер отдаёт `Access-Control-Allow-Origin: "*"` на эти
эндпоинты, а это несовместимо с credentialed-запросом по спеке CORS,
браузер сам блокирует такую комбинацию.

## 2. `company_id`

**Подтверждено:** простой ключ `company_id` **прямо в `localStorage`**
сайта (обычная строка, не JSON, не внутри токена). Ручной override:
`ChatApi.setCompanyId('<id>')`.

**Отвергнутая гипотеза:** `company_id` как JWT-claim по аналогии с
`user_id`. Реальный декодированный токен содержит только
`{sub, exp, nbf, iat, jti, device_id, user_id}` — `company_id` там нет.

## 3. `bot_id`

Источник — URL текущей страницы (SPA-роут вида `/bots/{bot_id}/...`,
точный путь не подтверждён отдельным document-запросом, но
проверяется тривиально по адресной строке). Альтернативный источник —
полный список через `POST /api/bots/v1/search` (см. п.6).

## 4. Список/детали чата

### `POST /api/chats/v1/search`
```json
{
  "bot_id": "...",
  "limit": 20,
  "offset": 0,
  "filter": {
    "filters": [{"operator": "is", "field": "assign_id", "value": "<id менеджера>"}],
    "logic": "and",
    "timezone": "Europe/Moscow"
  },
  "sort_direction": "desc"
}
```
Пагинация — **offset/limit**. Ответ: `{data: [...chats]}`, каждый чат
уже содержит `custom_fields`, `lead_id`, `lead.params`, `status`,
`assign_id`, `current_step_id`, `created_at`. Отдельный запрос по
одному чату для скана **не нужен** — всё уже есть в `search`.

Фильтр `assign_id` — опционален, без него (или с другим значением)
можно искать чаты другого сотрудника/без сотрудника (последнее — под
вопросом, см. «Открытые/непроверенные вопросы» ниже).

### `GET /api/chats/v1/{chat_id}`
Не нужен основному циклу скана (см. выше), но полезен для ручной
отладки одного чата. Форма ответа та же, что элемент массива из
`search`, обёрнутая в `{data: {...}}`.

## 5. `GET /api/leads/v1/{lead_id}/tracker-events`

`lead_id` — из `chat.lead_id`. Ответ:
```json
{"data": [{"event_type": "sale", "event_time": "ISO8601", "cost": 94, "currency": "USD"}]}
```

**Важно:** `event_type` приходит **с пробелами** (`"page view"`,
`"subscribe channel"`), не в `snake_case` — нормализация в
`snake_case` делается на нашей стороне (в `scanner.js` Chat
Summarizer), это не формат самого API.

Известные типы событий: `page view`, `click`, `subscribe channel`,
`contact`, `registration`, `fdfields`, `sale` (=FD), `resale` (=RD),
`last_rd`, `withdrawal_request`, `withdrawal` — список не
исчерпывающий, есть чек-боксы фильтра на фронтенде с этим же enum'ом,
могут быть другие значения.

Готовой сводки (депозит/вывод/баланс) API не отдаёт — считается
суммированием `cost` по типу на нашей стороне.

## 6. `POST /api/bots/v1/search` — список ботов

```json
{ "company_id": "...", "status": null, "type": null, "tags": null, "query": null }
```
**Без пагинации** (offset/limit тут не работают — дают 403 "access
denied", это была отвергнутая первая гипотеза). Ответ группирует
ботов по `space`:
```json
{
  "data": [
    {
      "space": {"id": "...", "name": "...", "access": {...}, "company_id": "..."},
      "bots": [{"id": "...", "name": "...", "access": {...}, "status": "active"}]
    }
  ]
}
```
Нужно самим уплощать `data[].bots` в простой массив.
`access.chat.read: "assigned"` встречается и на `space`, и на боте —
признак, что доступ может быть ограничен per-bot (см. риски
многоботового скана в TZ Chat Summarizer, п.0.6).

## 7. `GET /api/bots/v1/{bot_id}/custom-fields` — схема полей бота

Отдаёт реальный список ключей `custom_fields`, которые использует
конкретный бот. **Критично:** разные боты называют одно и то же поле
по-разному — подтверждено на примере `traider_id` (с «i») в одних
ботах и `trader_id` (без «i») в других. Любой поиск по `custom_fields`
должен проверять **все известные варианты написания**, не одно
жёстко зашитое имя:
```js
const TRAIDER_ID_KEYS = ["traider_id", "trader_id"];
```
Стоит дёрнуть этот эндпоинт на каждого бота хотя бы раз и свериться,
а не полагаться на один пример.

## 8. `POST /api/messages/v1/search` — история сообщений чата

```json
{ "chat_id": "...", "limit": 50, "cursor": "<опционально, из предыдущего ответа>" }
```

⚠️ **Форма ответа — не та, что можно было бы предположить.** Массив
сообщений лежит на уровень глубже, чем `data`:
```json
{ "data": { "items": [ /* сообщения */ ], "cursor": "..." } }
```
(Отвергнутая гипотеза: `{data: [...]}` напрямую — так предполагалось
изначально, реальность оказалась `{data: {items, cursor}}`; это была
живая причина бага с пустым контекстом перевода.)

Пагинация — **курсорная**, не offset/limit: следующая страница —
тот же `chat_id`/`limit` плюс `cursor` из ответа предыдущей страницы.

Сообщение:
```json
{
  "id": "...",
  "chat_id": "...",
  "type": "message",
  "status": "ready",
  "content": "текст (пусто, если это файл/голосовое)",
  "created_at": "ISO8601",
  "published_at": "ISO8601",
  "sender_type": "incoming",   // incoming = собеседник, outcoming = оператор
  "sender": "",                 // uuid оператора, если outcoming; пусто для incoming
  "external_id": "...",
  "read": true,
  "reply_message_id": "...",    // опционально
  "meta": { "template_id": "..." },   // опционально, для сообщений из шаблона
  "files": [
    {
      "id": "...",
      "type": "voice",
      "url": "https://prod-chatterfy-v1-files.s3.../file.<любое расширение>",
      "status": "ready",
      "meta": { "duration": 27, "file_size": 575993 }
    }
  ]
}
```

⚠️ **Поправка к более раннему предположению:** голосовые — не всегда
`.ogg`. В одном реальном примере голосовое пришло как `.mp3`
(оригинальное имя файла с пробелами и кириллицей, percent-encoded в
URL). Код не должен полагаться на конкретное расширение — просто
скачивать по `files[].url` и передавать как есть в STT-модель (она
сама определяет формат по содержимому/заголовкам, не по расширению).

## 9. `POST /api/flows/v1/search` — сценарий (flow) бота

```json
{ "bot_id": "..." }
```
Ответ (в HAR-экспорте иногда приходит в base64 — это особенность
экспортёра HAR, не самого API, декодировать перед парсингом):
```json
{
  "data": [
    {
      "id": "...", "name": "FD FLOW 2.0", "bot_id": "...",
      "created_at": "...", "order": 0,
      "steps": [
        {
          "id": "...", "name": "Where are you from",
          "type": "ai-reply",
          "flow_id": "...",
          "config": { /* для ai-reply — goal/requirements для ИИ, не готовый текст */ },
          "meta": { "x": 0, "y": 0 },
          "created_at": "..."
        }
      ]
    }
  ]
}
```
У бота может быть несколько сценариев (`flows`) одновременно. Типы
шагов, встреченные на практике: `send-message` (готовый текст лежит в
шаге), `ai-reply` (нет фиксированного текста, вместо этого
цель/инструкция для ИИ), `change-tags`, `assign-operator`,
`send-webhook`, `ab-router`, `start`, `custom-push`.

`chat.current_step_id` (из п.4) — ссылается на `step.id` отсюда:
показывает, на каком шаге сценария сейчас находится чат. Использовать
для анализа точки отвала (см. Chat Summarizer, раздел «Воронка», п.7.6)
— но `current_step_id` сам по себе не значит «отвалился», нужен ещё
фильтр по давности неактивности (см. соответствующий раздел TZ).

## 10. Второстепенные эндпоинты (проверены, но пока не пригодились)

- `POST /api/chats/v1/stats` — только счётчик чатов по статусам
  (`{"status":"finished","count":122}`), **без временных меток
  переходов** — не годится для SLA/времени разрешения.
- `POST /api/bots/v1/{id}/custom-stats` — личные счётчики («мои
  чаты», избранное, непрочитанные), не про SLA и не про деньги.
- Персональные настройки сайта (`user-settings`) — язык интерфейса,
  `input_translation_language` (у Chatterfy, похоже, УЖЕ есть какая-то
  собственная настройка перевода ввода — стоит присмотреться отдельно,
  не исследовано глубже).

## 11. Открытые/непроверенные вопросы (не гадать дальше без проверки)

- Как фильтровать чаты **без назначенного менеджера** —
  `filter.filters` с `operator: "is_null"`/`value: null`/`value: ""`
  на поле `assign_id` — ни один вариант не подтверждён трафиком, нужна
  ручная проверка (см. соответствующую задачу в Chat Summarizer).
- Точное имя ключа в `localStorage`/`sessionStorage`, где лежит JWT
  (п.1) — найдено по факту содержимого, не зафиксировано явным именем
  ключа.
- Есть ли у `messages/v1/search` разумный верхний предел `limit`
  (пробовали 50 — работает; больше не проверяли).
